# Backend Testing Guidelines v1

## Зачем писать тесты на бэкенде
• Тесты пишем ради стабильности API, безопасности финансовых транзакций и скорости деплоя, а не ради покрытия.
• Защита от регрессий при изменении схем БД и Protobuf.
• Безопасный рефакторинг высоконагруженных компонентов.
• Гарантия корректности сложной бизнес-логики (биллинг, сессии).
• Проверка конкурентного поведения (concurrency, гонки данных).

## Что покрываем Unit-тестами
• Валидаторы запросов и парсеры токенов.
• Чистую бизнес-логику в слое Service (сервисные правила, расчет стоимости поездки).
• Генераторы и менеджеры JWT-токенов.
• Чистые функции конвертации и маппинга данных.
• Обработку специфичных доменных ошибок.

## Что НЕ покрываем Unit-тестами
• Конфигурационные файлы и переменные окружения.
• Простые DTO/структуры (генерируемый Protobuf-код). *Отдельно: я тебе написал в качестве задания, чтобы начать привыкать. В реальной разработке ессно это не нужно, елси контракт валидный, то protoc сгенерирует всё как надо.*
• Сторонние библиотеки и драйверы баз данных без обертки.
• Pass-through код в контроллерах, который просто прокидывает вызов дальше.

## Хороший Unit-тест на Go
• Проверяет поведение, а не реализацию (тестируем экспортируемые методы слоев).
• Не зависит от реальной сети, Docker-контейнеров и боевой базы данных.
• Не зависит от порядка запуска и может выполняться параллельно (`t.Parallel()`).
• Использует табличные тесты (Table-driven tests) для проверки краевых значений.
• Читается как понятный сценарий (Given / When / Then или паттерн Arrange / Act / Assert).

## Integration & Highload рекомендации
• Изоляция базы данных: использовать Testcontainers (Docker) или `pgxpool` транзакции со встроенным Rollback для очистки данных после каждого теста.
• Проверка конкурентности: использовать флаг `go test -race` для отлова состояний гонки в интерцепторах и кэше.
• Тестирование лимитеров: эмулировать всплески RPS для проверки Redis Lua-скриптов (Rate Limiter, BruteForce).
• Идемпотентность: покрывать интеграционными тестами сценарии двойного списания/депозита (проверка механизма `SETNX` в Redis и `UniqueViolation` в Postgres).
• Имитация отказов: проверять работу retry-политик с помощью моков сетевых таймаутов от внешних провайдеров (например, MyMoney).

## Архитектура и тестируемость
• Dependency Injection: внедрять зависимости через интерфейсы (задавать контракты для репозиториев и внешних сервисов).
• Избегать глобального состояния: никаких глобальных переменных базы данных и `init()` функций, скрывающих подключение.
• Инжектировать Redis/БД клиент: передавать пулы соединений (`*pgxpool.Pool`) через конструкторы.
• Инжектировать Time provider: использовать интерфейсы вместо прямого вызова `time.Now()` для детерминированного тестирования TTL сессий и Grace Period.

## Test Pyramid

| Тип теста | Что проверяет |
| :--- | :--- |
| **Unit** | Изолированная бизнес-логика, хелперы, мапперы. |
| **Integration** | Взаимодействие слоев бэкенда (Service + DB / Redis / gRPC-интерцепторы). |
| **E2E / API** | Тестирование контрактов (gRPC/HTTP запросы к развернутому приложению). |
| **Load (Нагрузочные)** | Стабильность системы под высоким RPS, утечки памяти, деградация базы. |

## Когда тест стоит писать?
• Логика напрямую влияет на деньги (транзакции, биллинг).
• Есть сложные ветвления (if/else, switch), валидация и обработка ошибок.
• Есть конкурентный доступ к данным (Race conditions).
• Был обнаружен и исправлен критичный баг (защита от повторения).

## Регламент разработки бэка
1. Описание gRPC контракта (.proto файлы).
2. Реализация бизнес-логики и слоев (Clean Architecture).
3. Написание Unit и Интеграционных тестов.
4. Нагрузочное тестирование критических эндпоинтов (опционально, перед релизом).
5. Code Review и Слияние (Merge) через CI/CD пайплайн.
