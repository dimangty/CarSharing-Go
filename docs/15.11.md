Итого, главная идея --  в postgres читатели не блокируют писателей, а писатели не блокируют читателей. 
MVCC
Вместо того чтобы перезаписывать строку на диске при UPDATE:
1. Помечает старую версию строки как устаревшую.
2. Записывает рядом **новую версию** строки.

То есть, когда транзакция стартует, она получает "снимок" базы, snapshot, на текущий момент. Она видит только те версии строк, которые были закоммичены **до** её старта (или созданы ею самой). И в итоге, пока транзакция А обновляет строку, транзакция Б спокойно читает старую версию этой строки без каких-либо ожиданий и блокировок. В постгресе каждая версия строки называется кортежем (tuple) -- как в свифте. Помимо самих данных пользователя, в заголовке каждого кортежа лежат скрытые системные поля: xmin, ID транзакции, которая **создала** эту версию строки через INSERT. xmax -- ID транзакции, которая **удалила** или обновила эту строку DELETE/UPDATE. Если строка жива и актуальна, здесь стоит 0. Остальное ввиде адреса самой строки не нужно сейчас. 
*Первый пример*. Эти пеоля можно вывести простым запросом. Добавь что нить в таблицу(ну или прошлые записи остались), а потом `SELECT xmin, xmax, ctid, * FROM users;`
Упрощённый жизненный цикл(это тоже можно как шпаргалку оставить, полтому что это довольно таки важно понимать.)
1. Допустим, транзакция 100 вставила строку.
2. В базе лежит кортеж #1: xmin = 100, xmax = 0, name = 'Ivan'.
3. Приходит транзакция 105 и делает UPDATE users SET name = 'Petr'.
4. База не стирает 'Ivan'. Она меняет кортеж #1: xmin = 100, xmax = 105, name = 'Ivan'.
5. Рядом создается кортеж #2: xmin = 105, xmax = 0, name = 'Petr'.
6. Если транзакция 105 откатится через ROLLBACK, база просто пометит её как отмененную, и кортеж #1 снова станет валидным. Если закоммитится COMMIT --  кортеж #1 превратится в "мертвую строку" (dead tuple).
Теперь про блокировки -- Оптимистичная vs Пессимистичная блокировки. Оба подхода решают проблему Lost Update, когда два потока одновременно читают и перезаписывают одну и ту же строку. Первая -- пессимистичная блокировка (Pessimistic Locking). Суть: "Скорее всего, кто-то захочет изменить эти данные прямо сейчас, поэтому я заблокирую их заранее" То есть база физически на уровне движка не дает другим транзакциям менять строку, пока текущая транзакция не завершится.. Почти всегда, когда высокая конкуренция за одни и те же строки (например, списание баланса в каршаринге). Но так как у нас нет идеальных решений, всё от ситуации заивист, она снижает параллелизм, есть риск словить **Deadlock** 
*Второй пример*.
```sql
BEGIN;
-- Блокируем строку с id = 1 до конца транзакции. 
-- Другие транзакции, вызвавшие FOR UPDATE для этой строки, будут ждать.
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;

-- Делаем расчеты в коде и обновляем
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```
Вторая -- оптимистичная блокировка (Optimistic Locking)
Суть: "Вряд ли кто-то тронет эту строку параллельно со мной. Я не буду её блокировать, но при сохранении проверю, не изменилась ли она без меня". Реализуется на уровне приложения через дополнительную колонку( обычно version или updated_at).
Когда использовать: конфликты случаются редко, много операций чтения и мало записи (например, редактирование профиля пользователя или статьи). Минусы: сразу, если конфликт всё же случился, операцию придется повторять заново (retry) на уровне кода.
*Третий пример*
```sql
-- 1. Читаем данные вместе с текущей версией (допустим, version = 5)
SELECT balance, version FROM accounts WHERE id = 1;

-- 2. Пытаемся обновить, проверяя, что версия всё ещё 5
UPDATE accounts 
SET balance = balance - 100, version = version + 1 
WHERE id = 1 AND version = 5;

-- 3. В коде проверяем RowsAffected():
-- Если обновлено 0 строк — значит, кто-то успел обновить запись раньше нас. Делаем retry.
```
