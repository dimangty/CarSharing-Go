Вместо 2 строчек сразу сгенерируем 500 000 записей через `generate_series`. На 10 строках PostgreSQL вообще не использует индексы, а на полумиллионе разница будет видна глазами.

```sql
-- 1. Создаем таблицу заказов
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INT NOT NULL,
    status VARCHAR(20) NOT NULL,
    amount NUMERIC(10, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL
);

-- 2. Наливаем 500 000 тестовых записей за пару секунд
INSERT INTO orders (user_id, status, amount, created_at)
SELECT
    (random() * 50000)::int + 1,
    (ARRAY['new', 'paid', 'shipped', 'cancelled'])[floor(random() * 4 + 1)],
    (random() * 10000)::numeric(10, 2),
    NOW() - (random() * interval '365 days')
FROM generate_series(1, 500000);

-- 3. Проверяем, что данные на месте
SELECT * FROM orders LIMIT 10;

-- 4. Обновляем статистику для планировщика
ANALYZE orders;
```

Пока на самом верхнем уровне просто надо понимать, что индексы это а)специальные объекты, созданные для ускорения поиска б)основные виды -- B-Tree(как раз сбалансированные деревья) и composite(составные, когда индексом является не одно поле, а больше). Остальные можно пока не заморачиваться. Если кратко -- partial(частичные), GiST(для координат в основном), reversed(перевёрнутые B-tree, когда ищем не от вершины а от листьев) и Range(MIN, MAX храним). С ними будем разбираться по мере необходимости. 
Важно понимать, что то, что ты индекс добавил -- не гарантирует того, что он будет использовать. СУБД может сама решить, что от индекса больше вреда чем пользы. Например, если ты сделал так, что в ответе получится 50% данных от таблицы. Невыгодно скакать по страницам, постоянно дёргая их с диска, проще прочитать их вообще все, быстрее будет(Seq scan называется. и вообще, даже не 50%, а обычно если больше 5-10% от таблицы -- индекс скорее всего неиспользуется)

### EXPLAIN vs EXPLAIN ANALYZE + замеры до/после
EXPLAIN -- Показывает **план**, который придумал планировщик на основе статистики. Запрос **НЕ выполняется**
EXPLAIN ANALYZE -- Реально **выполняет запрос**, показывает реальное время в миллисекундах, реальное число строк и расхождения с прогнозом.
После того как накатишь те 500к на базу -- 
**Шаг 1. Запрос БЕЗ индекса:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE user_id = 4242 AND created_at > NOW() - INTERVAL '30 days';
```
Что значит: Seq Scan on orders, время выполнения около 40–80 мс, прочитано несколько тысяч страниц (Buffers: shared hit=...).
**Шаг 2. Добавляем составной индекс:**
```sql
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);
```
**Шаг 3. Повторяем тот же запрос С индексом:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE user_id = 4242 AND created_at > NOW() - INTERVAL '30 days';
```
Теперь -- Index Scan using idx_orders_user_created, время выполнения упало до 0.05–0.2 мс (ускорение в 200–500 раз), прочитано всего 3–5 страниц.

### Вот тут небольшая памятка в том числе на будущее -- когда индекс вроде есть, но база всё равно идет в Seq Scan (5 частых ловушек)

1. **Функция над индексированной колонкой:**
   `WHERE LOWER(email) = 'test@mail.ru'` или `WHERE DATE(created_at) = '2026-11-13'`. Индекс построен по сырому значению, а не по результату функции (решение: функциональный индекс или переписать условие на диапазон).
2. **Неявное приведение типов:**
   Колонка `phone` типа `VARCHAR`, а в запросе передали число без кавычек: `WHERE phone = 79991234567`. Postgres приведе́т колонку к числу на лету, и индекс отвалится.
3. **Поиск с `%` в начале строки:**
   `WHERE status LIKE '%paid'` — B-Tree отсортирован слева направо, он не знает, что в конце строки.
4. **Нарушение порядка в составном индексе:**
   Индекс `(user_id, created_at)`, а ищем только `WHERE created_at > ...`.
5. **Слишком большой процент выборки или маленькая таблица:**
   Если запрос возвращает больше ~10–15% строк всей таблицы (например, `WHERE status != 'cancelled'`), планировщик сознательно выберет `Seq Scan`, потому что последовательное чтение диска быстрее, чем миллион случайных прыжков по индексу.
